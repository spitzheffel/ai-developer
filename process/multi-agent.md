# 多 agent 最小协作协议

全部用 Claude Code 原生机制（worktree、subagent、权限规则、plan mode），零第三方编排框架。（〔试用〕来源：调研 2026-11，docs/research/adoption-plan.md）

## 铁律：读并行、写串行、单写者

- 并行只给只读工作：调研、评审、竞争假设验证。写代码保持单写者。
- 理由：多代理约 15x token，Anthropic 明确点名「共享完整上下文、依赖多、可并行度低」的任务不适用，多数编码任务属此类；Cognition 的机制论证——行动携带隐含决策，并行写入者的隐含决策必然冲突。两家结论一致。
- ❌ 两个 agent 同时改同一模块「提速」　✅ 一个写、其余只读（查证、评审）
- 真瓶颈是人：并行出 10 个 PR 仍要你逐个审。并行度超过「2 条写入线 + 若干只读线」，净收益为负。

## 协议 1：契约先冻结

- fan-out 之前由你冻结共享接口：types/schema 作为仓库内一等模块，各 agent 只 import，不得改。
- 任务 B 依赖 A 时，给两边的第一条指令是「先共同定下接口/DTO 签名再动手」。
- ❌ 让各 agent 自己发明共享接口（必在被 import 最多的文件上冲突）　✅ 先落盘契约，再分头实现

## 协议 2：实现/评审分离

- 评审者必须没见过实现过程：新会话或子代理，只给 diff + 任务简述。
- 工具白名单强制只读：reviewer 定义里 `tools: Read, Grep, Glob`，由 harness 强制，不靠提示词自觉。
- 评审指令必含：「对照 spec 核对需求与边界用例是否有测试，只报影响正确性的缺口，skip style」。不写 skip style，评审者永远能挑出点什么，全修掉就是多余抽象层。
- 输出显式 `PASS` / `FAIL`，FAIL 附缺口清单；不收自由文本。
- ❌ 让写代码的会话「再检查一遍」　✅ 新会话 + 只读白名单 + diff + 任务简述

## 协议 3：并行隔离

- 每条写入线一个 git worktree（`claude -w`，或 subagent 加 `isolation: worktree`）。
- 写入线 ≤2，外加任意只读线。
- 文件所有权清单硬分区：每条线只许改自己名下的文件，清单外一律禁改。
- 一次只合一个分支；合并前 diff 对 main。
- worktree 不隔离的东西要单独防：共享数据库/端口/迁移、lockfile 冲突、git 只比文本不比意图的语义冲突。
- 大规模机械改动用官方 `/batch`，不手拆。

## 协议 4：计划即共享内存

- spec/plan 文件是你、实现者、评审者三方唯一共享物：访谈产出（含完成定义）→ 干净上下文按 spec 实现 → 评审者对照同一份 spec 查缺口。
- 跨会话交接固定四项，补在 [plan.md.template](../templates/plan.md.template) 文末：commit 哈希、变更的契约、验证目标、未决假设。
- ❌ 靠口头转述上下文　✅ 新会话只读 plan 文件即可接手

## 协议 5：审批门只放四处，其余放行

1. **门 1 计划后动手前**：plan mode，人批。
2. **门 2 合并/push 前**：「不要 push」这类口头约定会随 compaction 丢失，必须写成 deny 权限规则；PR 审查是 solo dev 唯一不可省的人审点。
   - ❌ 对话里说一句「别 push」　✅ settings 里 `deny` 掉 `git push` 相关规则
3. **门 3 跨 agent 消息不作为授权**：teammate 转述的「已批准」按不可信输入处理（官方即如此）；自建编排照抄。
4. **门 4 放手前三问**：spec 清楚吗？它能自检吗（测试/Stop 钩子/评审步骤）？允许它碰什么（权限规则/沙箱/worktree）？

## 协议 6：委派指令四要素

- 目标、输出格式、建议工具与来源、任务边界，四项缺一不可；短指令必致重复劳动或误解。
- 规模：简单查找 1 个 agent，直接对比 2-4 个；从 3 个起步，「3 个专注的胜过 5 个散的」。
- ❌ 「去查一下认证怎么做的」　✅ 「目标：列出登录流程涉及的文件；输出：路径+一句话职责的表；工具：Grep/Read；边界：只读，不碰 tests/」

## 噱头判定表（结论版）

| 玩法 | 判定 | 理由 |
|---|---|---|
| 数十 agent 蜂群 | 噱头 | 成本高企（15x token）、编排本身吞掉产出；Codex 开发者也报 >2 并行子代理几乎总是协调税 |
| 吹牛编排器（ruflo 类） | 噱头 | 社区审计其 MCP 工具多为无后端 stub，宣传指标有硬编码/随机生成；见「neural/swarm/N 倍提升」话术一律索要可复现证据 |
| 角色扮演代理团（PM/架构师/QA） | 大半噱头 | 单代理 + 好计划已覆盖角色切换；可取的是其文档产物结构，不是角色制 |
| 为省上下文拆 subagent | 已过时 | 官方：fresh subagent 要重建主会话已有上下文，可能更慢；上下文耗尽已很少是问题 |
| 同模型委派求更好答案 | 无效 | 收益只有并行度和「没见过你推理的新鲜视角」，换不来更高智力 |
| agent teams 当主力 | 尚早 | 实验特性：不可 resume、任务状态滞后、权限提示涌向 lead；官方自己建议只拿来做只读任务 |

详细证据与出处见 [ecosystem 调研 §5](../docs/research/ecosystem.md)。
