> 阶段5 审查用。同一份清单过三遍:Claude Code 自审、干净上下文的二遍 AI 审查、你的人审。审的对象是 diff,不是整个仓库。

# 审查清单

vibe coding 真正的陷阱不是代码写错,而是 diff 大到没人看。本清单生效的前提是 diff 足够小——超限先拆,再谈审查。

## 0. diff 规模红线

单次审查超过约 **400 行改动**或 **10 个文件**:拒审,要求按 [plan.md](../templates/plan.md.template) 的方案步骤拆分重交。超限的「审查」只是走过场,等于没审。

## 1. 先审测试,再审实现

测试是实际生效的规格:实现错了,测试会叫;测试错了,没人叫。按此顺序:

1. **先读测试**,对每个测试问两个问题:
   - 它断言的行为,是不是 [任务简述](task-brief.md) 要的行为?
   - 实现写错时它会失败吗?(无断言、只测 happy path ≈ 没测)
2. **逐条对照任务简述的验收标准**:每条标准都要指得出对应的改动与测试;对不上号的改动,要么多余,要么跑题。
3. **新增逻辑是否有测试**:标准见 [完成定义](definition-of-done.md) 第 1 节。

## 2. AI 味代码清单(逐项扫 diff)

| # | 症状 | 判定 |
|---|---|---|
| 1 | 重复造轮子 | 项目里已有同功能实现;按功能关键词搜过再下结论 |
| 2 | 过度防御 | 对类型上不可能为空的值做 null 检查;try-catch 包住不会抛错的代码 |
| 3 | 吞异常 | catch 后只 log,不处理也不向上抛 |
| 4 | 无意义注释 | 注释只是复述代码行为 |
| 5 | 类型逃逸 | `any` / `as any` / `@ts-ignore` / `# type: ignore` 出现且没有一行理由说明 |
| 6 | 过度抽象 | 单一实现配接口;只被使用一次的工厂或包装层 |
| 7 | 死代码与未使用导出 | 新增但没有调用方的函数、导出、参数、配置项 |
| 8 | 风格不一致 | 命名、错误处理、文件组织与周边代码不同;以所在栈文档「## 5. 参照模式」为准 |

对照示例:

- ❌ `if (user != null)`,而 `user: User` 类型上不可能为空(症状 2)
- ✅ 直接使用;真可能为空,去修类型定义,而不是加防御
- ❌ `// 遍历所有订单` 挂在 `for (const order of orders)` 上面(症状 4)
- ✅ 注释只写「为什么」:`// 上游 API 偶发 429,退避重试三次`

## 3. 三遍审查的分工

| 遍 | 谁 | 做什么 |
|---|---|---|
| 一 | Claude Code 自审 | 提交审查前对照第 0–2 节逐项自查,能改的当场改掉 |
| 二 | 干净上下文的 AI 审查 | 新开会话,只给 diff + 任务简述 + 本清单;再跑一轮减法审查:「删掉哪些代码不影响验收?」 |
| 三 | 你的人审 | 只聚焦测试与验收标准;AI 味问题应已在前两遍清零 |

## 流程串联

分步小 diff(习惯)→ 自审对照本清单 → 二遍 AI 审查 + 减法审查 → 人审聚焦测试与验收 → 通过后进入阶段6,见 [完成定义](definition-of-done.md) 第 4 节。

审查中反复出现的新症状,记入 [痛点日志](../docs/pain-log.md)(pain log);重复两次以上,按 [三连筛](../CLAUDE.md) 决定沉淀为配置/钩子、CLAUDE.md 还是规则(阶段8 沉淀)。
