# ADR 规范

ADR 把「为什么这么选」落盘，防止知识蒸发，也让 AI 不在没依据时推翻旧决策。

## 目录与命名

- 位置：项目内 `docs/adr/`，文件名 `NNNN-短标题.md`（四位递增序号）。
- 每篇一个决策，一页以内。

## 五段式

1. **标题**：含序号与日期，如 `# 0007 用 Postgres 存会话（2026-11-05）`。
2. **状态**：`提议` / `已采纳` / `已被 NNNN 取代`。
3. **背景**：触发决策的约束与压力，2-4 句。
4. **决策**：选了什么，一句话起头。
5. **后果**：得到什么、放弃什么、新增的约束。

## append-only

- 已采纳的 ADR 不改正文。决策变了，新开一篇，旧篇状态改为 `已被 NNNN 取代`（只改这一行）。
  ❌ 直接改写 0007 的决策段 ✅ 新开 0012，把 0007 状态改为「已被 0012 取代」

## 什么时候写：三条件同时成立

1. **难逆转**：改回去要付出明显代价。
2. **未来读者会惊讶**：不看理由会以为是错的。
3. **真实权衡过**：确实比较过至少一个替代方案。

缺一条就不写，防止 ADR 膨胀成流水账。
❌ 为「用 prettier 格式化」写 ADR（可逆、不惊讶） ✅ 为「不用 ORM、手写 SQL」写 ADR

## 触及旧决策

改动触及已有决策时，PR 须引用对应 ADR 编号，或新增一篇 ADR；不允许悄悄绕过。
（〔试用〕来源：调研 2026-11，docs/research/adoption-plan.md）

## 示例

```markdown
# 0003 不用 ORM，手写 SQL（2026-11-05）
状态：已采纳
背景：查询多为跨表报表，ORM 生成的 SQL 难调优；团队只有一人，熟悉 SQL。
决策：数据访问层用 sqlc 从 SQL 文件生成类型安全代码，不引入 ORM。
后果：得到可控的查询性能；放弃自动迁移与关系导航；新表需手写 SQL 与迁移文件。
```

与其他文件的关系：CLAUDE.md 模板的「项目约定」节已写入「触及旧决策须引用或新增 docs/adr/」，见 [CLAUDE.md.template](../templates/CLAUDE.md.template)。
