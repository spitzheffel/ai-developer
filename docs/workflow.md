> 本库总纲:用 Claude Code 做 vibe coding 全链路开发的掉坑地图与对策索引。写给第一次通读本库的你,以及"被坑了但不知道该查哪个文件"的时刻。参考文档,按需打开,不要放进常驻上下文。

# vibe coding 全链路工作流

阶段0 环境底座 → 阶段1 需求表达 → 阶段2 方案 → 阶段3 实现 → 阶段4 验证 → 阶段5 审查 → 阶段6 提交 →(下一个任务回到阶段1)┃ 阶段7 会话管理贯穿全程 ┃ 阶段8 沉淀把每次踩坑回流到上游

## 落点五类图例

每条对策都标注落点——它最终以什么形态存在于仓库或你的操作里:

| 标记 | 形态 | 成本特征 |
|------|------|----------|
| `[配置/钩子]` | 工具强制执行,违反即报错或自动修复 | 配一次永久生效,零注意力成本 |
| `[CLAUDE.md]` | 常驻上下文:命令速查、模块地图、范例指针 | 占每个会话的 token 预算,必须少而硬 |
| `[模板]` | 按需复制填空的结构 | 用时才加载 |
| `[规则]` | prose 规则,只写模型默认会做错的事 | 最贵:每多一条都稀释整体遵守率 |
| `[习惯]` | 你自己的操作方式,不写进任何文件 | 靠重复养成 |

三连筛的顺序就是这张表从上往下:能进配置/钩子的绝不写成规则,能靠上下文解决的也不写成规则。

## 两个总结论

**① 症状在下游,根因在上游。** 翻车现场集中在阶段3 实现和阶段4 验证:造轮子、改飞无关文件、谎报完成。但照[痛点日志](pain-log.md)回溯,根因多半在阶段0(它不知道你的命令、配置和范例)、阶段1(你没说清,它用互联网最常见做法补全)和阶段7(上下文早就烂了还在继续用)。在实现阶段逐条打补丁,不如往上游修一次底座。

**② 真正的 prose 规则不到三分之一。** 把下文全部对策按落点数一遍:大头是配置/钩子、上下文(CLAUDE.md 与范例)、模板和习惯,剩下才轮到规则——这正是[三连筛](../CLAUDE.md)筛完的样子。所以本库是 文档+配置+模板+钩子 的工具包,不是规则大全。

## 阶段0 环境底座

开工前把工具链、配置、CLAUDE.md 一次配好。这里的投入在之后每个会话里复利。

**【典型掉坑】**

- 猜测试命令:项目用 pnpm + vitest,它跑 `npm test`;失败后还顺手生成一个 package-lock.json 污染仓库。
- 风格漂移:没配 formatter/linter,产出风格取决于互联网平均值,同一个文件里混着三种写法。
- 权限弹窗疲劳:每个 `pnpm test`、`mkdir` 都弹确认,你开始无脑点允许,真正危险的命令也被顺手放行。

**【对策】**

- `[CLAUDE.md]` 命令速查:把测试/构建/lint/typecheck 的准确命令写进项目 CLAUDE.md,从 [CLAUDE.md 模板](../templates/CLAUDE.md.template)起步。
- `[配置/钩子]` lint/format 一次配齐:直接取各栈现成配置——[typescript-react](../stacks/typescript-react/README.md)、[python](../stacks/python/README.md)、[go](../stacks/go/README.md) 的 configs/;没有你的栈,按[栈模板](../stacks/_template.md)自建一份。
- `[配置/钩子]` PostToolUse 钩子在每次编辑后自动格式化([post-edit-format.sh](../claude-code/hooks/post-edit-format.sh)),风格问题从此不占上下文、不费口舌,做法见 [hooks](../claude-code/hooks.md)。
- `[配置/钩子]` permissions 白名单:高频安全命令免确认,危险操作保留弹窗,见 [settings.json.example](../claude-code/settings.json.example)。

核心认知:CLAUDE.md 是唯一保证每次都在场的上下文——会话会被 /clear、会被压缩,只有它每次完整重载。配得上"每次在场"的信息才写进去,细节放按需加载的文档。

## 阶段1 需求表达

**【典型掉坑】**

- 一句话需求"加个导出功能":导出格式、入口位置、要不要进度条……所有没说的决定,它都用互联网最常见做法补全,而不是你的偏好。
- 加戏:让它修一个按钮,它顺手重构了整个组件,还"优化"了三处无关逻辑。
- 缩水:需求里隐含的边界情况(空列表、权限不足、并发)被静默跳过。
- 错误假设埋得深:它对数据模型的一个误解,直到第 15 个文件的 diff 才暴露。

**【对策】**

- `[模板]` 分级任务简述:小任务三行说清,中大任务用完整模板(任务简述/非目标/完成定义),见[任务简述](../process/task-brief.md)。
- `[规则]` "非目标"专治加戏:❌ 只写要什么 ✅ 同时写不要什么——「非目标:不动现有样式、不升级依赖、不重构」。
- `[习惯]` 中型以上任务,先让它复述理解并列出假设,确认后再动手。纠正一句话的假设,比纠正一片 diff 便宜得多。

## 阶段2 方案

**【典型掉坑】**

- 跳过方案直接写:中型任务上来就改文件,方向错了只能整体推倒,烧掉的是你审 diff 的时间。
- 口头确认的方案被上下文压缩弄丢:聊半小时敲定的设计,长会话压缩后只剩大意,后半程它按自己的理解重新发明。

**【对策】**

- `[习惯]` plan mode:中型以上任务先进 plan mode,方案没确认不落一行代码——在方案阶段纠错的成本,约是 diff 阶段的十分之一。
- `[模板]` 方案确认后立即落盘:写成 [plan 文件](../templates/plan.md.template),拆成可验证的分步 checklist。文件不会被压缩,新会话也能直接续上。

## 阶段3 实现

**【典型掉坑】**

- 没利用已有资产:仓库里 `utils/http.ts` 已封装重试与鉴权,它没搜就重写了一个;为格式化日期又引入新依赖,而仓库已有 date-fns。
- 风格漂移加顺手改无关:新代码和周边文件长得不像(自创一套目录与写法),diff 里还混着两个"顺手优化"的无关文件。
- 幻觉 API:凭"这个库应该有"写出不存在的方法和参数签名,运行时才炸。
- 一把梭大改:一个回合改 20 个文件,中间哪步错了无法定位,只能整体回滚。

**【对策】**

- `[CLAUDE.md]` 模块地图 + 新建前先搜:在 CLAUDE.md 维护"做 X 去 Y 文件"的模块地图;写任何通用函数前先搜已有实现。
- `[CLAUDE.md]` 范例驱动:在 CLAUDE.md 指认参照文件——「新组件照 `src/components/UserCard.tsx` 写」。一个干净范例胜过十条风格规范。
- `[规则]` 只改与任务相关的文件:❌ diff 里出现任务简述没提的文件 ✅ 想顺手改的记下来,单开任务。
- `[规则]` 引新依赖先征求同意,选型按各栈 README 的选型清单走。
- `[规则]` 通用能力(重试/缓存/鉴权/日期处理)动手实现前,先做显式的 轮子vs自研(build-vs-buy) 决策,绝不自研清单见 [build-vs-buy](../process/build-vs-buy.md)。
- `[规则]` 不确定的 API 先查文档或读源码再写:❌ 凭记忆补全签名 ✅ 查不到就明说查不到。
- `[习惯]` 分步可运行:大改按 plan 拆步,每步结束可编译可运行,用 checklist 文件逐项打勾跟踪。

栈特有的坑与参照实现,见各栈 README 的「5. 参照模式」与「6. 高频 AI 坑」。

## 阶段4 验证

**【典型掉坑】**

- 谎报完成:"已完成并通过测试",实际从头到尾没跑过任何命令。
- 为变绿作弊:测试不过就删测试、加 skip、放宽断言,而不是修实现。
- 修 bug 不留证据:直接宣布"修好了",没有失败测试证明 bug 存在过,也无法证明修复有效。
- UI 改动只看代码不看渲染:样式塌了、按钮飞了,它看不见,照样报完成。

**【对策】**

- `[规则]` 完成定义:说"完成"之前必须跑过的命令清单,见[完成定义](../process/definition-of-done.md)。
- `[配置/钩子]` Stop 钩子在收工前强制跑 lint/typecheck/vet/build 等快检,任一失败即打回;它不跑测试,也判不了完成声明的真伪——测试仍按完成定义手动跑并贴出输出:见 [hooks](../claude-code/hooks.md) 与 [stop-verify.sh](../claude-code/hooks/stop-verify.sh)。
- `[规则]` 修 bug 铁律:❌ 直接改代码宣布修好 ✅ 先写失败测试复现,再修到变绿。
- `[习惯]` UI 改动让它用 Playwright 截图自查,看真实渲染结果,而不是想象渲染结果。
- `[配置/钩子]` 检查必须快:常跑检查保持在分钟级——测试慢到十分钟,人和 AI 都会跳过它。慢测试挪去 CI,本地留快速子集。

## 阶段5 审查

**【典型掉坑】**

- diff 大到没人看:一次 800 行,你扫两眼就合并——这是 vibe coding 真正的陷阱:代码进了主干,但没有任何人理解它。
- AI 味代码积累:过度防御的 try/catch、复读代码的注释、用不上的抽象层。单个无害,积累成泥潭。
- 测试没人审:实现错了,测试跟着错,绿色的测试从此锁死错误行为。

**【对策】**

- `[习惯]` 从源头控 diff:按方案分步走,每步一个十分钟内能读完的小 diff(呼应阶段2/3 的分步)。
- `[习惯]` 干净上下文二遍审查:开新会话或子代理、不带写码过程的上下文专门审一遍;再加一遍减法审查——"这个 diff 里哪些可以删"。
- `[规则]` 重点审测试,测试即规格:断言是否真的描述需求、有没有被悄悄放宽,逐条清单见[审查清单](../process/review-checklist.md)。

## 阶段6 提交

**【典型掉坑】**

- 巨型 commit:"fix bugs and refactor" 一口气 30 个文件,回滚和 bisect 都无从下手。
- 脏东西进历史:草稿文件、调试脚本、.env 里的密钥跟着 commit 一起进了 git 历史。

**【对策】**

- `[规则]` conventional commits + 原子提交:一个 commit 对应方案的一个步骤。❌ `update code` ✅ `feat(export): add CSV download endpoint`。规范并入[完成定义](../process/definition-of-done.md)的提交规范节。
- `[配置/钩子]` .gitignore 卫生:.env、草稿目录、构建产物提前列入——防呆优于提醒,检查项同见[完成定义](../process/definition-of-done.md)。

## 阶段7 会话管理

**【典型掉坑】**

- 一个会话干五件事:前四件的失败尝试塞满上下文,第五件的产出质量断崖下跌。
- 上下文压缩丢细节:长会话自动压缩,早先确认过的关键决定被压没,它开始自相矛盾。
- 沉没成本:同一个问题纠正了五轮还在原会话里挣扎,"再说一遍它就懂了"——不会。

**【对策】**

- `[习惯]` 一会话一任务,任务结束就 /clear。
- `[习惯]` 重要信息落盘:方案、决定、进度写进文件(plan、checklist),文件不会被压缩,新会话可直接续上。
- `[规则]` 止损:同一问题两次纠正无效 → 回滚代码 + 开新会话 + 换更好的任务简述重来。❌ 第五轮"这次你听懂了吗" ✅ 回滚重开。对会话要克服沉没成本:重开比恋战便宜。
- `[习惯]` 大范围探索(全库找用法、多文件调研)交给子代理,主会话只收结论,不被中间过程污染。

操作细则与判断阈值见[会话管理](../process/session-management.md)。

## 阶段8 沉淀

**【典型掉坑】**

- 同一个坑每个会话踩一遍:每次都口头纠正,从不固化,纠正本身成了重复劳动。
- 规则只增不减:CLAUDE.md 涨到 300 行,最重要的 10 行被淹没,整体遵守率反而下跌。

**【对策】**

- `[习惯]` 会话中发现值得永久记住的事当场落盘,不攒"回头再说":直接说「把这条加到 CLAUDE.md」或用 `/memory` 编辑;`#` 快捷追加官方文档未确认,以实测为准。
- `[习惯]` 每次被坑先记[痛点日志](pain-log.md),再按三连筛归位:能工具强制 → 配置/钩子;因缺上下文 → CLAUDE.md/范例;剩下 → 规则。
- `[配置/钩子]` 重复出现的工作流(发布、脚手架、数据修复)固化成自定义 skill,一句话调用。
- `[习惯]` 定期删:不再踩的坑,对应规则删掉,守住各文件行数预算。规则库和代码一样会腐烂。
